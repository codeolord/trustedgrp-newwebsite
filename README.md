# Trusted Verifier — marketing site

A complete, multi-page marketing website for a digital certificate and badge platform. Static HTML/CSS/JS, generated by a small Node script with **zero dependencies**.

## Run it

```bash
npm run dev     # build + serve on http://localhost:4321 and rebuild when src/ changes
npm run build   # write the static site to dist/ and check every internal link
npm start       # build once and serve
```

Deploy to Hostinger by running `npm run build`, then uploading the **contents** of `dist/` into `public_html` (including `.htaccess`). The build includes Apache directory-index routing, a custom 404 page and disabled directory listings. The same `dist/` output can be uploaded to other static hosts; Vercel is configured in `vercel.json` to build and serve it. Pretty URLs such as `/pricing` map to `/pricing/index.html`; `sitemap.xml` and `robots.txt` are generated too.

The Hostinger upload is static. The live support chat and staff inbox still need the Vercel API and Neon database described below; see the Hostinger embed instructions to connect the chat widget to that API deployment.

## Live support chat

The site includes a visitor chat widget and a private staff inbox at `/support`. On Vercel, the chat API uses serverless functions and Neon PostgreSQL. The database tables and indexes are created automatically when the API is first used.

Configure these Vercel environment variables for Preview and Production:

- `DATABASE_URL`: the Neon PostgreSQL connection string.
- `SUPPORT_ADMIN_PASSWORD`: a strong shared staff password (at least 16 characters).
- `SUPPORT_SESSION_SECRET`: a private random secret of at least 32 characters, used to sign staff sessions and pseudonymize rate-limit identifiers. Do not reuse the database password.

### Form submissions

Run [`sql/forms.sql`](sql/forms.sql) in the Neon SQL Editor to create the form-submission and short-lived rate-limit tables. Deploy the updated project to Vercel with `DATABASE_URL` set, and point `api.trustedgrp.com` to that Vercel project as described below. The Hostinger contact, affiliate and newsletter forms send to `https://api.trustedgrp.com/api/forms`; the API only allows the trusted site origins and stores validated fields in `public.site_form_submissions`. Review new entries in Neon with:

```sql
SELECT id, form_type, name, email, form_data, created_at
FROM public.site_form_submissions
WHERE status = 'new'
ORDER BY created_at DESC;
```

Submissions are stored in Neon; this setup does not send email notifications or newsletter campaigns automatically.

`neon deploy` writes `DATABASE_URL` and other Neon settings to `.env.local`, which is ignored by Git. The app's `lib/support.js` uses `DATABASE_URL` with `@neondatabase/serverless`; `vercel dev` loads `.env.local` for local API functions. Neon does not automatically copy local values into Vercel's hosted environment, so configure them there separately. The support password and session secret are not generated by Neon; add those privately for local use and in Vercel. Neon Auth is enabled for the project, but the support inbox continues to use its existing shared staff password.

Project-scoped Neon agent skills are in `.agents/skills/`, with versions recorded in `skills-lock.json`. The VS Code workspace MCP server is in `.vscode/mcp.json`, uses OAuth, and is pinned to this Neon project; VS Code will ask you to sign in on first use. The existing user-level Neon skills and MCP setup are unchanged. Check or update project skills with `neon skills status` and `neon skills update -y`.

Redeploy after setting environment variables. Staff can sign in at `https://your-domain/support`; the session is HTTP-only, secure, and expires after 12 hours. Visitors start a chat from the existing help button; replies are checked every four seconds while the chat is open. The visitor session token is stored in a secure HTTP-only cookie and only its hash is stored in Neon.

Generate a session secret locally with `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"` and add the output directly to Vercel without sharing it in chat or committing it to the repository.

For local API testing, use the Vercel CLI (`vercel dev`) with the same environment variables. The built-in `npm run dev` static server does not run Vercel API functions.

### Embed chat on the Hostinger site

The public `trustedgrp.com` website is hosted separately from this Vercel project. To keep the current Hostinger website and use its Neon-backed support inbox:

1. In the Vercel project, add the custom domain `api.trustedgrp.com`. Add the exact DNS record Vercel requests in Hostinger; leave the apex and `www` records unchanged.
2. Set `DATABASE_URL` to the rotated Neon pooled connection string, `SUPPORT_SESSION_SECRET` to a private value of at least 32 characters, and `SUPPORT_ADMIN_PASSWORD` to a staff password of at least 16 characters in Vercel Production. Redeploy after saving the variables.
3. In Hostinger File Manager, edit `public_html/index.html`. Remove the old Tawk.to embed if replacing it, then add this script just before `</body>`:

   ```html
   <script src="https://api.trustedgrp.com/assets/hostinger-support.js" defer></script>
   ```

The loader opens the standalone `/support-widget` page in a same-site `api.trustedgrp.com` iframe, so chat API requests and secure visitor cookies stay on that subdomain. Staff can open `https://api.trustedgrp.com/support`. Keep the site's other markup and assets unchanged.

## Project layout

```
build.js            generator + internal link checker
serve.js            dev server (with --watch)
src/site.js         brand name, domain, emails, social links  ← rename the product here
src/layout.js       <head>, header + mega menus, mobile nav, footer, help widget
src/ui.js           components and SVG generators (certificates, badges, documents, app mockups)
src/icons.js        inline icon set + logo mark
src/data/*.js       content: features, solutions, integrations, templates, blog, customers…
src/pages/*.js      one module per page group; each exports [{ path, title, description, body }]
src/assets/         styles.css, main.js (all interactions), favicon.svg
```

To add a page, add an object to any `src/pages/*.js` export (or a new module listed in `PAGE_MODULES` in `build.js`).

## Before going live

- **Brand:** Update the name, domain and contact addresses in `src/site.js`. The shared logo lockup is `src/assets/logo.svg`; the compact mark is in `src/icons.js` and `src/assets/favicon.svg`.
- **Placeholder content:** customer names, logos, quotes, statistics, prices and team members in `src/data/content.js`, `src/pages/pricing.js` and `src/pages/company.js` are fictional. Replace them with real ones.
- **Legal text:** the privacy, terms and cookie pages are templates with a visible notice. Have them reviewed before publishing.
- **Forms:** contact, affiliate and newsletter forms validate on the client and show a success state, but they don't send anything yet. Demo booking opens Calendly directly. Wire forms up in `src/assets/main.js` (search for `TODO`).
- **Certificate generator:** it parses the prompt with keywords on the client. Swap `parse()` in `main.js` for a call to your model or API if you want real AI generation.
